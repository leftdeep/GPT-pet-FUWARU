# 流式播放改造与空间精简清单

日期：2026-10-09。版本沿用 0.52。用户确认采用只解码当前/待切换动作的小内存缓冲方案。

## 本次落地

- WebM 通过 FFmpeg 标准输出按需解码，不生成整段 BGRA .raw 文件，不再启动时解码全部动作。
- 最多两个解码器，每个缓冲六帧。640×640 时这些缓冲合计最多 18.75 MiB；两份在途帧最多另占 3.125 MiB。WPF 视频/图片帧缓存预算为 56 MiB，另计偷看图、过渡图和框架/解码器自身内存；这是缓存预算，不是进程总内存承诺。
- 视频最长解码边提高到 640。保留已有透明通道、逐帧锚点、走路分段、校色和菜单定义。移除单段 256 MiB 和整包 1 GiB 的裸帧体积限制。
- 后台解码、界面线程生成 Bitmap；等待时保持上一幅画面和变换。重新播放、前后跳帧和快速切换都支持。错误视频通过 LoadWarning 呈现，不生成不透明矩形。
- 原生检查使用明确的精确读帧模式，并另外测试实际异步读帧路径。完整帧数验证使用无落盘的 ValidateAsync。
- 启动时清理本播放器旧格式 vp9-bgra-v1-*.raw；其他类型文件及仍被旧程序打开的文件不会被误删。回退到旧播放器会重新生成旧缓存。
- .gitignore 新增 output/、verification/ 和 animation/*.mov，防止制作缓存、验证截图和 MOV 默认再次纳入 Git。不会自动清除已经写入 Git 的对象。

640 解码支持并不会给已有 384 成品补出原图细节。高清候选位于 output/quality-preview-20261009；正式替换仍需遵循已审核动画的原有流程，尤其开心/害羞的 reviewedFinal，不可偷换为重新校准的 MOV。

## 验证与实测

编译零警告、零错误；443 项核心检查、10 项发布流程检查、默认回退皮肤的576 项原生 smoke 和 71 项菜单检查通过。当前完整13段素材另测822项，全部通过。新版本已安装，当前桌宠保持 Size=240、右侧吸附及原有位置，9 个预览菜单动作、13 个视频分段继续使用原素材。

完整素材补测同时修正了两处测试时序：模拟用量期间取消界面对真实账号/本地日志刷新的订阅，避免测试额度被覆盖；菜单重置闲置计时在 Opened 事件内观察，并等待实际打开事件，避免随后合法的时钟推进造成误判。真实用量更新行为沿用原逻辑。

系统 TEMP 的旧库原有 14 个裸帧文件，合计 1,016,266,752 字节（969.1875 MiB）。运行中的旧实例曾占用其中 13 个；正常退出并切换新版本后再次检查，旧库文件数为 0。

## DSH 为什么小，以及应该学什么

本地 DSH 的 106 个播放 WebM 共 51.83 MiB，平均 0.489 MiB/动作；整个外层开发目录约 968.69 MiB 逻辑大小。它大量使用硬链接，去重后 NTFS allocated 约 862.57 MiB。动画数量不是主要空间来源。

它用 VP9 Alpha、24 fps、640×360、CRF 40，并用两个 video 槽位播放需要的压缩文件；没有本项目原来的完整 BGRA 磁盘库。源码、母版、制作中间文件和 GIF 预览与运行包分开。参考：
[编码脚本](https://github.com/PC2005-cloud/dsh-pet/blob/main/scripts/encode_thumbs.py)；
[桌面播放器](https://github.com/PC2005-cloud/dsh-pet/blob/main/dsh-pet/runtime/electron-helper/sprite.js)。

我们采用按需播放和运行包分离的思路，保留 C#/WPF；不用为减小体积迁移 Electron。也不直接照抄 CRF 40：用户已选优先清晰度，640/CRF18 样片的压缩大小仍可接受。

推荐后续把目录分为：
1. 运行包：一个发布程序、被清单引用的 WebM/偷看图、FFmpeg、必要 .NET 运行时、启动脚本、用户存档。
2. 开发/制作工作区：源码、SDK、审核基准、必要标注缓存和 JSON。
3. 历史存档：较旧验证证据、旧发布、母版和 Git 快照。

运行包按现有素材粗算约 290 MiB（未压缩，含 .NETCore/WindowsDesktop 与 FFmpeg），已有合适系统运行时可再少约171 MiB。相比整个制作工作区更适合长期日常使用与分享。把开发目录移到同一磁盘不会释放磁盘，只会让运行目录更小；历史归档需要实际移出或按保留策略删除才会减少总占用。
